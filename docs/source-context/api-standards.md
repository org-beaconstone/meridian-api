Integration rules for payment flows at **Meridian Bank**. These exist because payment calls are not ordinary HTTP calls: a retry in the wrong place moves real money twice, and a missing circuit breaker turns one degraded provider into a full checkout outage.

Every provider integration follows these patterns. If a provider cannot be integrated within them, that is a **technical fit failure** under the [Payment Provider Expansion Playbook](https://beacon-stone.atlassian.net/wiki/spaces/SPT/pages/147947579/Payment+Provider+Expansion+Playbook), not a reason to bend the standard.

## Architecture

| Component | Stack | Responsibility | Talks to providers? |
| --- | --- | --- | --- |
| `meridian-web` | React / TypeScript | Checkout UI, payment method selector, provider abstraction layer | NO |
| `meridian-api` | Java / Spring Boot | Payment orchestrator, pluggable provider interface, routing logic, webhooks | YES |
| `meridian-mobile` | Swift + Kotlin | Shared payment SDK, native UI | NO |

Provider-specific behaviour belongs behind the provider interface in `meridian-api` and nowhere else. We are live with Adyen and Worldpay.

Some provider-specific handling still leaks outside the abstraction from the Worldpay onboarding. **MAPI-771** covers that cleanup and should land *before* the next provider integration starts.

## Authentication patterns

- **Provider credentials never leave **`meridian-api`**.** Not in the browser, not in the mobile SDK, not in a build artifact
- Credentials are held in the secret store and rotated on a documented schedule. Rotation must be possible without a deploy
- Each provider implements the `ProviderCredentials` contract. If a provider needs mutual TLS, that is configuration on our side, not a new code path
- Inbound **webhooks are verified by signature on every request**. An unverified webhook is dropped and alerted on, never processed optimistically
- Webhook endpoints are idempotent. Providers retry, and duplicate delivery is expected behaviour rather than an error condition

## Idempotency

Every state-changing provider call carries an idempotency key generated by `meridian-api` and persisted *before* the call is made.

- The key is derived from our own payment intent ID, never from a timestamp or random value generated at call time
- If we cannot persist the key, we do not make the call
- On an ambiguous response — timeout, connection reset, 5xx — we replay with the **same** key rather than generating a new one

## Retry and fallback

The rule we care most about: **never retry a payment call whose outcome is unknown without the original idempotency key.**

| Provider response | Retry? | Notes |
| --- | --- | --- |
| Network timeout, connection reset | YES | Same idempotency key, exponential backoff with jitter |
| 5xx from provider | YES | Same key, max 3 attempts |
| 429 rate limited | YES | Respect `Retry-After` when present |
| Soft decline | NOT TO SAME PROVIDER | Eligible for fallback routing |
| Hard decline | NO | Terminal. Surface to the customer |
| 4xx validation error | NO | Our bug. Alert, do not retry |

Backoff is exponential with jitter, capped at 3 attempts and a hard ceiling on total elapsed time. A customer sitting on a checkout spinner is a failed payment regardless of what the retry eventually returns.

**Soft versus hard decline classification is provider-specific and must be mapped explicitly** in the provider implementation. Defaulting unknown codes to "soft" causes retry storms. Unknown codes map to **hard**. See the SCA notes in the [Payments Compliance and Regulatory Policy](https://beacon-stone.atlassian.net/wiki/spaces/SPT/pages/147980346/Payments+Compliance+and+Regulatory+Policy).

Fallback routing sends an eligible failed attempt to the paired failover provider. A provider is never both primary and sole option in a corridor. Fallback is only attempted when the first attempt is confirmed *not* to have captured funds.

## Circuit breakers

Every provider sits behind its own breaker in `meridian-api`. Breakers are per provider **and per corridor**: a provider degraded in one market should not remove it from a healthy one.

| State | Behaviour |
| --- | --- |
| CLOSED | Normal operation |
| OPEN | Trips on sustained error rate or latency breach over a rolling window. Traffic routes to the paired failover provider |
| HALF-OPEN | Small probe volume after a cooldown. Success closes the breaker, failure reopens it with a longer cooldown |

## Timeouts

- **Authorisation calls** — short timeout, fail fast into fallback
- **Capture and refund** — longer timeout, these are not customer-blocking
- **Reconciliation and reporting** — run out of band, never in a request path

No payment call inherits a default client timeout. Every one is set explicitly.

## Observability

Each provider call emits a structured event with provider, corridor, latency, outcome and idempotency key. Dashboards are per provider and per corridor. We alert on error rate, latency, breaker state and reconciliation variance.

Reconciliation variance is the one that matters most and the one teams forget. A provider can look perfectly healthy on latency while settling incorrectly.

## Adding a new provider

1. Implement the provider interface in `meridian-api` behind a feature flag, default off (**MAPI**)
2. Map decline codes explicitly, including soft versus hard
3. Implement webhook signature verification and idempotent handling
4. Prove the reconciliation export parses end to end
5. Add dashboards and alerts before any live traffic
6. Update the payment method selector in `meridian-web` (**MWEB-318**)
7. Mobile only once the hardcoded provider config is removed (**MMOB-402**)

Steps 1 to 4 are **Phase 1 sandbox exit criteria** in the [Payment Provider Expansion Playbook](https://beacon-stone.atlassian.net/wiki/spaces/SPT/pages/147947579/Payment+Provider+Expansion+Playbook).
